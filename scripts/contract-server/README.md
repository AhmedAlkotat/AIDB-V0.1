# AIDP contract server

A **development and testing tool**. It is **not** the backend, it is **not** part of the application, and it proves nothing about
the real FastAPI backend, whose contract is **not agreed**. It implements the *proposed* contract in
[`docs/api/openapi.draft.yaml`](../../docs/api/openapi.draft.yaml) with deterministic fixtures, so the frontend's HTTP adapters
(the asynchronous document service, the API client, the error mapping, the in-memory token handling) can be exercised before the
backend exists.

```
npm run contract-server                       # listens on http://127.0.0.1:5301
node scripts/contract-server/server.mjs --port 5400
```

Point the frontend at it (see `.env.example`):

```
VITE_API_MODE=http
VITE_API_BASE_URL=http://127.0.0.1:5301/api/v1
```

In Wave 1 only the document service has an HTTP adapter; every other service still reports "not connected" in `http` mode (their
adapters are Wave 2), so the full UI cannot be driven against this server yet. The tests (`tests/contractServer.test.js`) drive it
through the real API client and the real HTTP document service.

## What it does

* Every operation of the draft is in the route table (`ROUTES`), implemented or answered with `501` in the standard error envelope
  (the five backup operations). A test fails when the table and the draft differ.
* Auth: `POST /auth/login` returns an access token in the body and the refresh token **only** as an HttpOnly cookie;
  `/auth/refresh` exchanges the cookie; deactivating an employee ends their sessions at once (decision 16).
* Documents: multipart registration with the server-side checks (type 415, size 413, selected pages 422, malformed selection 400,
  storage full 507), ownership (an employee's other documents are `404`), the archive/queue views, filters, sorting and paging,
  canonical content built with the frontend's own pure domain functions, the original download with an RFC 5987 Arabic file name.
* Saving drafts: the **document lock** is checked on every write (`lockLost` / `lockHeld`), the write names the pages it changes and is
  all-or-nothing (**page isolation**), and `baseRevision` protects against lost updates and stale approvals (`409 revisionConflict`
  with `currentRevision`).
* Reprocessing: a page job; its result becomes a **candidate** and replaces nothing until accepted; accepted results and rejected
  attempts are logged as metadata only.
* Approval and versions: owner or Admin approves, only the Admin creates a new version, the previous approved version is kept, an
  approved document is read-only.
* Export: JSON is built from the **latest approved version** (selected and approved pages only, original order, `sourcePage`, no
  internal source). DOCX/XLSX/PDF are generated by the real backend (decision D3); here a clearly labelled stand-in with the right
  type and file name is served (`X-AIDP-Fixture: true`). It is **not** a valid document.

## Fixtures

Fixed ids, names and timestamps on every start (`fixtures.mjs`): the accounts `employee` / `employee2` / `admin` / `disabled`
(fixture passwords of this tool only), and the documents `fx-ready` (Ready for Review, class invoice), `fx-approved` (approved version 1),
`fx-other` (the other employee's) and `fx-pending` (Pending, queue position 1).

## Simulation controls (not part of the contract)

`POST /__contract/<name>` with a JSON body: `reset`, `expire-access-tokens`, `revoke-refresh`, `fail-next {status, code, times}`,
`advance-clock {ms}` (expires locks and tokens), `bump-revision {documentId}` (another writer got in), `process {documentId}` (the AI
queue finishes), `complete-job {jobId}` (a reprocessing result arrives), `set-storage-full {full}`, `take-lock {documentId, userId}`.

State is in memory; it listens on `127.0.0.1` only.
